# /review — GAS アプリの場合の追加ルール

> SKILL.md の 5 つの観点（抜け・過剰・解釈ずれ・副作用・安全）と報告のトーンはそのまま使う。ここに書いたことだけ、GAS 向けに足す。

## 「安全」観点の読み替え

日々のレビューでは、次の 3 点を見る（公開前の総点検は `/secure`）：

1. **秘密情報の置き場** — API キーが `.gs`・`.html` に直接書かれていないか。`PropertiesService.getScriptProperties()` から読んでいるか
2. **画面に返している値** — 画面から呼ばれる関数の戻り値に、秘密情報・他の人のデータ・シート全体のデータが含まれていないか（画面に届いた値はブラウザから誰でも見られる）
3. **初めて動き出すコード** — SKILL.md と同じ。今回の変更で初めて呼ばれる関数・初めて触るシートがあれば、それも確認の対象に含める

## 受け入れ基準の照合

AC を「確かめ方」で分けて報告する：

- **自動テストの AC** → 対応するテストがあり、緑かどうか
- **確認用 URL の AC** → コードを読んで、対応する実装（`.gs` の戻り値・`.html` の表示処理）があるかを見る。画面での確認は、レビュー報告のあとに利用者と行う（下の「レビューのあと」）

報告の例：

```
### 仕様を満たしている箇所 ✅
- AC-2「期限切れと判定される」→ Code.gs の isOverdue で対応、テスト緑 ✅
- AC-3「期限切れは赤で表示」→ index.html で赤の表示に対応。このあと確認用 URL で確かめます

### 気になる点
- AC-1「締切を日付で入力できる」の入力欄が、タスク追加の画面に見当たりませんでした
```

## レビューのあと：確認用 URL で受け入れ基準を確かめる

GAS アプリでは、レビュー報告のあとに **確認用 URL を開いて、人の目で受け入れ基準を確かめる**。仕様とのズレをレビューで直してから確かめるので、確認のやり直しが起きない。

1. **気になる点を直した場合は、先にテストと保存（push）をやり直す**（`skills/implement/gas.md` の「保存（push）」の手順）。直さない場合はそのまま 2 へ
2. spec の AC のうち **「確かめ方: 確認用 URL」になっているもの** と、**既存の主な操作 1 つ**（副作用の確認）をチェックリストにして利用者に渡し、1 つずつ一緒に確かめる：

```
確認用 URL を開いて、次の 3 つを確かめてみてください：
- [ ] AC-1 締切を日付で入力できる（タスク追加の画面に日付の欄があり、選べる）
- [ ] AC-3 期限切れのタスクが赤で表示される（過去の日付で 1 件追加してみてください）
- [ ] もともとの操作：タスクを 1 件追加して、一覧に出る

違っていたら、AC の番号を添えて教えてください。
```

- 既存の操作を 1 つ入れるのは、自動テストが届かない画面・保存の部分は、ここでしか副作用に気づけないため
- 自動テストが緑なのに画面が違う場合は、**判定の結果を画面に渡す部分**（`.gs` の戻り値、`.html` の表示処理）がずれていることが多い。そこから調べる
- 違っていた項目を直したら、テスト・保存（push）をやり直し、その項目をもう一度確かめてもらう
- 結果（確かめた / まだ）は、最後の報告の「確認用 URL で確かめた項目」に書く

## Google 側との食い違い

- 利用者が Google 側のエディタで直接書き換えた形跡（PC 側にない関数がある、など）を見つけたら、勝手に上書きせず報告する
  > 「Google 側にだけある変更があるようです。次の保存（push）で消えてしまうので、先に PC 側に取り込みますか？（`clasp pull` で取り込めます）」
